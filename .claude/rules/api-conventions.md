# API conventions

## HTTP API (`teamcraft-server`, axum)

- Request/response types live in `teamcraft-proto` so clients share them; they derive
  `Serialize`/`Deserialize` and `utoipa::ToSchema` for the OpenAPI spec.
- One handler per file module, named after the handler (`create_channel_handler.rs`).
- Handlers return `Result<Json<{Action}Response>, {Feature}Error>`; the error enum implements
  `IntoResponse` and maps each variant to a status code.
- Error bodies: `{ "error_code": "channel_not_found", "message": "..." }`. `error_code` values are
  stable and part of the API.
- Handlers stay thin: parse → check permissions (shared helper) → call a service function → map
  the result. No SQL and no crypto in handlers.
- Versioned under `/api/v1/`. Breaking changes need a new version or a compatible transition.

## Gateway (WebSocket) and SFU signaling

- Messages are tagged enums in `teamcraft-proto` (`#[serde(tag = "type")]`) with an `Unknown`
  catch-all on the client side.
- Every event carries a monotonically increasing sequence number per connection so clients can
  resume after reconnect.

## Database

- Postgres, accessed only through the DB crate (`teamcraft-db`, from M1).
- Compile-time checked `sqlx::query!` / `query_as!`; commit the `.sqlx/` offline data.
- Migrations in `migrations/`, forward-only, never edited after merge.
- Primary keys are Snowflake IDs (`BIGINT`), generated by the server, wrapped in newtypes.
- Large or growing tables (`messages`, `mls_messages`) are partitioned by time from the first
  migration.

## Configuration

- One TOML file plus environment overrides (`TEAMCRAFT_…`); example file `teamcraft.example.toml`
  documents every option with its default.
- Instance policies that admins change at runtime (retention, guest rules, `admin_self_join`, …) live
  in the database as signed policy, not in the TOML file.
