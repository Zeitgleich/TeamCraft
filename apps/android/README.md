# TeamCraft for Android

A thin Kotlin/Jetpack Compose shell over the Rust client core (ARCHITECTURE.md §8, PLAN.md M8). All
encryption, sync and storage logic is in `teamcraft-core`, reached through the UniFFI bindings of
`crates/teamcraft-ffi`. The app does login, keys in the Android Keystore, screens, push and
notifications.

## Layout

| Path                                           | What                                                                           |
|------------------------------------------------|--------------------------------------------------------------------------------|
| `app/src/main/java/.../auth`                   | OIDC login with AppAuth (code + PKCE), session sealed with a Keystore key      |
| `app/src/main/java/.../server`                 | Server entry: stored servers, managed configuration, `server-info` fetch       |
| `app/src/main/java/.../security`               | `KeystoreBox` (AES-256-GCM key in the Keystore), `SealedFile`                  |
| `app/src/main/java/.../core`                   | Opens the Rust core per account (Keystore-sealed key); chat bridge and models  |
| `app/src/main/java/.../push`                   | `PushBackend`s, UnifiedPush receiver, payload format                           |
| `app/src/full/java/.../push`                   | FCM (flavor `full` only)                                                       |
| `app/src/main/java/.../notifications`          | MessagingStyle notifications with reply / mark-as-read (Android Auto)          |
| `app/src/main/java/.../calls`                  | Telecom calls (Core-Telecom), in-call screen and service, Android Auto calling |
| `app/src/main/java/.../ui`                     | Compose screens and the view model                                             |
| `app/src/main/java/uniffi`, `src/main/jniLibs` | Generated by `scripts/build.sh` (not in git)                                   |
| `docker/Dockerfile`                            | Build image                                                                    |
| `scripts/`                                     | `docker-build.sh` (host), `build.sh` and `emulator-test.sh` (in the container) |

### How the app talks to the core

`TeamCraft` (Kotlin, generated) is one object per signed-in account. Calls are `suspend` functions;
inside, one Rust engine thread owns the store, the client and the sync loop (the core's futures
are single-threaded). The app hands in access tokens (`TokenProvider`, backed by AppAuth with
refresh) and gets `onChange` callbacks (`EventListener`), on which screens re-read. Sync runs while
the app is in the foreground (`ProcessLifecycleOwner`); in the background, push wakes the app.

Chat features go through a JSON bridge instead of a typed call each: `snapshot`, `messageWindow`,
`act` and `query` exchange the same `ChatSnapshot` / `MessageWindow` / `ChatAction` / `ChatQuery` /
`ChatAnswer` messages (teamcraft-client-api `remote`) that the desktop shell exchanges with its
webview. `core/Wire.kt` mirrors the view models as plain `@Serializable` data, `core/ChatActions.kt`
builds actions and queries, `core/ChatClient.kt` decodes the answers; all logic stays in the core.
`apiRequest` reaches plain server endpoints (notification settings, meetings) with the session's
token.

## Build

Everything builds in a container; nothing but Docker is needed on the host.

```sh
docker build -t teamcraft-android-build:local apps/android/docker
TEAMCRAFT_ANDROID_CACHE=/path/on/a/big/disk apps/android/scripts/docker-build.sh
```

| Piece        | Version                                                                           |
|--------------|-----------------------------------------------------------------------------------|
| Base image   | `rust:1.99.1-slim-trixie` + OpenJDK 21, `cargo-ndk` 4.1.2, cmdline-tools 11076708 |
| Android SDK  | platform 37.0, build-tools 36.0.0, NDK 28.2.13676358 (installed into the cache)   |
| Gradle / AGP | Gradle 9.8.2 (wrapper), Android Gradle Plugin 9.4.0, Kotlin 2.4.21                |
| Rust targets | `aarch64-linux-android` (phones), `x86_64-linux-android` (emulator)               |

`TEAMCRAFT_ANDROID_CACHE` (default `~/.cache/teamcraft-android`) holds the SDK, NDK, Gradle and
Cargo caches and the Rust target directory: about 7 GB, 11 GB with the emulator. The image itself
stays small, which matters when Docker's disk is tight.

`scripts/build.sh` builds the Rust library (release, both ABIs), generates the Kotlin bindings with
`teamcraft-uniffi-bindgen` and runs Gradle. Without arguments it builds the debug APKs of both
flavors and runs the unit tests; other Gradle tasks can be passed:

```sh
apps/android/scripts/docker-build.sh assembleFullRelease
```

APKs end up in `app/build/outputs/apk/<flavor>/<type>/`. For a quicker build, `TEAMCRAFT_RUST_PROFILE=dev`
builds the core without optimizations and `TEAMCRAFT_ANDROID_ABIS=x86_64` for the emulator only
(the Kotlin bindings come from the x86_64 library, so it always stays in the list).

CI (`.github/workflows/android.yml`) runs `docker-build.sh` with the dev profile for both ABIs:
`assembleFullDebug` and the unit tests of both flavors, whenever `apps/android` or a crate the app
links changes.

|---------|---------------------|--------------------------------------------|
| `full`  | FCM and UnifiedPush | Google Play                                |

### Configuration

Gradle properties (`gradle.properties` has the defaults; override with `-P` or in
`~/.gradle/gradle.properties`):

| Property                       | Meaning                                                                          |
|--------------------------------|----------------------------------------------------------------------------------|
| `teamcraft.defaultServer`      | Server pre-selected on first start (self-built apps); empty: the user enters it  |
| `teamcraft.pushGatewayUrl`     | Push gateway the FCM token is sealed for (publisher builds); empty: the server's |
| `teamcraft.oidcRedirectScheme` | Redirect URI is `<scheme>:/oauth/callback`; the server's client must allow it    |
| `teamcraft.fcm*`               | Firebase project of the deployment (flavor `full`); empty: no FCM                |
| `teamcraft.upload*`            | Upload signing key (see "Signing")                                               |

### Server address

No server is built in. On first start the app asks for the server address (docs/operations.md
"Server address in the apps"): the user types `team.example.com`, a full URL, or pastes an invite or
message link. The core normalises it (`normalizeServerAddress`), the app fetches
`GET {origin}/api/v1/server-info` (no redirects, 10 s connect / 15 s read timeout, at most 1 MiB)
and the core checks the answer (`checkServerInfo`). The app then shows the server's brand and host
for confirmation and signs in with the identity provider, client and scopes the server announced.
The redirect URI must be in the server's `redirect_uris`.

| Failure                                            | What the user reads                                             |
|----------------------------------------------------|-----------------------------------------------------------------|
| Not a web address, user name in it, plain `http`   | Invalid address / https only                                    |
| Another web server, or a 404                       | Not a TeamCraft server                                          |
| HTML page or redirect (hotel Wi-Fi)                | Sign in to the network first                                    |
| DNS, refused, timeout                              | Offline (retried when the device is back online) or unreachable |
| Certificate or TLS failure                         | No secure connection                                            |
| 5xx                                                | Server not available                                            |
| Version checks                                     | App too old / server too old                                    |
| Sign-in settings invalid, redirect URI not allowed | Ask the admin                                                   |

The checked server profile is stored per account (`server/ServerStore.kt`, app-private preferences,
excluded from backups) and checked again on every start (`storedServer`); a profile that doesn't
pass leads back to the entry. Everything of an account is keyed by the server's storage key:
`auth/<key>/session.bin`, `store/<key>/<subject>/`, `keys/<key>/<subject>.key`, `brand/<key>/`.
"Change server" on the sign-in screen forgets the server's profile (local data stays); signing out
keeps the server. The app only ever contacts servers the user entered or the managed configuration
names, never one a server points to. Builds from before the server entry kept one unkeyed session
and store: the first start moves them aside to `legacy/` and the user signs in (and links the
device) again. `auth/LegacySignOut.kt` then signs the old session out: when the user enters the
server it belonged to (same identity provider and client), it unregisters the old device's push
with the old session and revokes its refresh token; after 14 days without that server it revokes
the token alone. Then `legacy/` is deleted. The core (`legacy_session`) decides which provider may
get the token.

A self-built app can set `teamcraft.defaultServer`: it is checked on first start and shown for
confirmation like a managed server, but the user can still change it.

#### Managed configuration (MDM)

Organizations set the server through Android Enterprise managed configuration
(`res/xml/app_restrictions.xml`); it takes precedence over `teamcraft.defaultServer` and is read on
every start.

| Key           | Type   | Meaning                                                                                                                       |
|---------------|--------|-------------------------------------------------------------------------------------------------------------------------------|
| `server_url`  | string | Server address; with no account yet the app checks it and goes straight to the confirmation                                   |
| `lock_server` | bool   | Only `server_url` is allowed: no "Change server", other addresses are refused, and an account on another server is signed out |

### Tests

- Unit tests (JVM, both flavors) run with every build: the server entry (start decision, managed
  configuration precedence, the lock, error texts, storage paths, stored accounts), notification texts, push payload decoding,
  the UnifiedPush subscription JSON, sidebar sections, what each wake-up kind shows, notification
  line order and dismissal matching, ring matching, the DND schedule JSON and quick-DND times
  across DST.
- Instrumented tests (`app/src/androidTest`) run the Rust core on a device: library loading via JNA,
  the engine thread, the sealed store, error mapping, and the Keystore sealing; and the notification
  channels, posting and removing conversation and incoming-call notifications. On a headless
  emulator in the container (needs `/dev/kvm`; run a normal build first):

  ```sh
  apps/android/scripts/docker-build.sh --emulator
  ```

- `crates/teamcraft-ffi` has its own Rust tests, including a dev-stack test where a mobile client
  and a desktop-style client exchange messages.

## Running against the dev stack

Start the dev stack and the server (repository README). On the emulator (or a USB device):

```sh
adb reverse tcp:8080 tcp:8080
adb reverse tcp:8081 tcp:8081
adb install app/build/outputs/apk/full/debug/app-full-debug.apk
```

Enter `http://127.0.0.1:8081` as the server address. Debug builds accept plain HTTP to any host
(`src/debug/res/xml/network_security_config.xml`), e.g. `http://10.0.2.2:8081` or a machine on the
LAN, but the issuer the server announces must be reachable from the device under the same name:
Keycloak writes the host the device used into the token's issuer, and the server accepts only its
configured issuer, which is why `adb reverse` and `127.0.0.1` are the easy way. The dev realm's
public client `teamcraft` already allows the redirect URI `de.zeitgleich.teamcraft:/oauth/callback`.
Release builds allow plain HTTP only to the device itself (`127.0.0.1`, `localhost`, `::1`).

## Security

- **Database key:** 32 random bytes, sealed with a non-exportable AES-256-GCM key in the Android
  Keystore (StrongBox where present). The store is plain SQLite with every record sealed by the core
  (e2ee.md §9.2), because SQLCipher needs a libcrypto the NDK doesn't ship.
- **OIDC session:** AppAuth's state (refresh token included) is sealed the same way.
- **Backups:** off, and every domain excluded from cloud backup and device transfer. A new phone is
  set up by linking it from another device or with the recovery passphrase.
- **TLS:** the core trusts the Mozilla root set (`webpki-roots`) on Android; HTTPS is required except
  for the device itself (and any host in debug builds, see above).

## Push and notifications

The server sends only an encrypted wake-up (e2ee.md §7); the app opens it with the device's push
key, fetches and decrypts the message and builds the notification itself.

| Service     | Registration token sent to the server                             | Wake-up on the wire                                                   |
|-------------|-------------------------------------------------------------------|-----------------------------------------------------------------------|
| FCM         | The FCM registration token                                        | Data-only message, key `w`: the sealed wake-up, base64url, no padding |
| UnifiedPush | Web Push subscription JSON `{"endpoint", "keys": {p256dh, auth}}` | Web Push (RFC 8291) body = the sealed wake-up; the connector decrypts |

The server sends both (`crates/teamcraft-server/src/push`): UnifiedPush through its Web Push sender,
since the token has the same shape, and FCM through the HTTP v1 API with the format above, directly
(`[push.fcm]`, self-built apps) or through the push gateway (store apps, `docs/push-gateway.md`).

Notifications use `MessagingStyle` (sender as `Person`, group conversations titled with the
channel), category `MESSAGE`, and two actions that don't open the app: reply (`RemoteInput`,
`SEMANTIC_ACTION_REPLY`) and mark as read (`SEMANTIC_ACTION_MARK_AS_READ`). Replies are appended to
the notification.

| Wake-up   | What the app does (`notifications/PushDecision.kt`)                                                    |
|-----------|--------------------------------------------------------------------------------------------------------|
| `message` | Adds the message to its conversation's notification (see below); a duplicate re-posts it silently, an urgent repeat alerts again; nothing when the device's own mute/DND check says so (counted for the diagnostics) |
| `call`    | CallStyle incoming-call notification with a full-screen intent, plus a Telecom call; stops after 45 s    |
| `dismiss` | With a call ID: stops ringing; otherwise removes the read lines of the conversation or thread           |
| `test`    | A short confirmation on the `other` channel                                                            |

One notification per conversation (tag = conversation ID) with a long-lived conversation shortcut and
a group summary that carries the badge; lines are ordered by message time and deduplicated by
message ID, and kept sealed in app storage so a new process continues them (deleted on sign-out).
Every high-priority FCM wake-up shows or updates a notification, since FCM deprioritises apps that
show nothing. A wake-up that takes longer than about 8 s continues as expedited work
(`push/WakeUpWork.kt`).

| Channel          | Importance | For                                   |
|------------------|------------|---------------------------------------|
| `messages`       | default    | Channels and groups                   |
| `mentions`       | high       | DMs, mentions, urgent messages        |
| `incoming_calls` | high       | Rings (ringtone, full-screen intent)  |
| `calls`          | default    | The ongoing call (foreground service) |
| `other`          | low        | Test pushes, background work          |

Settings has "Do not disturb" (quick DND through presence, weekly schedule, exceptions; stored on
the server) and "Notification diagnostics" (push service and UnifiedPush distributor, system
switches, battery state, DND state, pushes received, test push). The app never asks to be exempt
from battery optimisation: FCM relies on high-priority messages, and with UnifiedPush the
distributor is the app that must run in the background (it raises this app to the foreground per
message), so the guidance links to the distributor's settings.

## Android Auto

Messaging works through the notifications above: Android Auto reads `MessagingStyle` notifications
aloud and sends voice replies through the reply action, provided the app declares
`com.google.android.gms.car.application` with `<uses name="notification"/>` (done,
`res/xml/automotive_app_desc.xml`). To test, enable Android Auto's developer mode and "Unknown
sources" (sideloaded apps are hidden otherwise), or use the Desktop Head Unit.

Calls are Telecom calls (Jetpack Core-Telecom, `calls/CallController.kt`): the system rings for
incoming calls, shows the call on the lock screen, routes audio to Bluetooth and car kits, and holds
our call for a cellular one. The media and the end-to-end encryption run in the Rust call engine
(`TeamCraft.joinCall`, `CallSession`), on a call thread of its own; `CallService` keeps the
microphone alive with the ongoing-call notification.

On Android Auto, `calls/CarCallService.kt` (a `CarAppService` in the category
`androidx.car.app.category.CALLING`) lists direct and group conversations and starts their calls;
the car's own in-call screen then shows the Telecom call. Google lists the calling category as beta:
it is accepted only on Internal and Closed Testing tracks (PLAN.md §8), which suits a company app
distributed through Closed Testing. Release builds only accept the hosts in the Car App Library's
allowlist; debug builds accept every host (Desktop Head Unit).

Calls are audio-only on Android so far, and the microphone runs without platform echo cancellation
(cpal's AAudio input doesn't use the voice-communication preset); use a headset or the car kit
until the call engine gets the `VOICE_COMMUNICATION` input preset or WebRTC's echo canceller.

## Signing

One key signs every channel: the GitHub release APKs, the App Bundle for Google Play and (later)
other stores. It is a self-generated key that is registered with Play App Signing as the app signing
key, so an APK from GitHub and the Play install update each other. Release builds take it from
properties outside the repository:

```properties
# ~/.gradle/gradle.properties
teamcraft.uploadKeystore=/secure/path/teamcraft.p12
teamcraft.uploadKeystorePassword=...
teamcraft.uploadKeyAlias=teamcraft
teamcraft.uploadKeyPassword=...
```

Set up once per publisher; never replace the key afterwards (installed apps only accept updates
signed with it, and a lost key can't be reset):

1. Create it: `keytool -genkeypair -v -storetype PKCS12 -keystore teamcraft.p12 -keyalg RSA -keysize
   4096 -validity 10000 -alias teamcraft`. Keep a backup outside the build machines (a password
   manager).
2. Play Console → the app → *Test and release → App integrity → Play App Signing*: choose *Use a
   different key* → *Export and upload a key from Java keystore*, download `pepk.jar` and the
   encryption key, and run the command the page shows with this keystore and alias. pepk needs an
   OpenJDK (Oracle's JDK rejects its unsigned BouncyCastle provider). Upload the encrypted output.
   Register no separate upload key: Play then accepts bundles signed with this key.
3. For the release workflow, add it as the secrets `ANDROID_UPLOAD_KEYSTORE_BASE64` (`base64 -w0
   teamcraft.p12`), `ANDROID_UPLOAD_KEYSTORE_PASSWORD`, `ANDROID_UPLOAD_KEY_ALIAS` and
   `ANDROID_UPLOAD_KEY_PASSWORD` (docs/release.md).

The certificate's SHA-256 (`keytool -list -v -keystore teamcraft.p12`) is the one Play App Signing
shows as the app signing key certificate and the one `apksigner verify --print-certs` prints for a
release APK.

## Google Play closed testing

1. Create the app in the Play Console with the deployment's application ID (`de.zeitgleich.teamcraft`
   by default; change `applicationId` for your organization).
2. Build `bundleFullRelease` (an AAB) with the key above, and upload it to the **Closed testing**
   track. Releases do this automatically for the internal testing track (docs/release.md, "Google
   Play"). Testers enter the server address, or the organization sets it through managed configuration.
3. Add the testers (an email list or a Google Group of employees) and share the opt-in link.
4. Fill in the data safety form: messages are end-to-end encrypted, the server sees metadata
   (e2ee.md §4.4); no ads, no analytics.
5. Android Auto: declare messaging and calling in the app's Play Console "Android Auto" setting.
   The calling category is beta and only allowed on Internal and Closed Testing tracks: keep the
   app there (a production release with the CALLING category is rejected until Google opens it).

## Not done yet

- iOS (needs macOS; the Swift side uses the same `teamcraft-ffi`).
- While a device link waits for the other device, other calls into the core wait too (one engine
  thread runs one job at a time).
- Screen sharing from the phone and background effects (desktop only).
- Keywords and the first name can only mark messages that reach the phone: with the push level
  "mentions" the server pushes explicit mentions only (it can't read the text).
- Received video is decoded with Cisco's OpenH264, which the phone downloads on the first call
  (licensing, see teamcraft-media `openh264_library`); without it calls stay audio-only for that
  phone. Sending uses the phone's hardware encoder. Video is untested on real devices so far.
