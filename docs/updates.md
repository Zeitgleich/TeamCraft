# Desktop updates

How the desktop app stays current, and how organizations control it; the Android libre app's F-Droid
repository is in §8. Release mechanics are in [release.md](release.md); the signed workspace
policy in [admin.md](admin.md) §2.3.

## 1. Goals

- Windows, macOS and AppImage installs **update themselves**: checked in the background, downloaded
  in the background, applied on restart. Nothing interrupts work, and nothing ever restarts the app
  during a call.
- deb and rpm installs are updated by the **system package manager** from signed APT and RPM
  repositories; the app tells the user and can ask PackageKit to do it. A package installed from a
  downloaded file gets a link to the new file instead.
- Flatpak installs are updated by **Flatpak**; the sandboxed app never replaces itself, but it
  checks the feed and tells the user.
- **Organizations decide**: an owner-signed policy can disable self-updates, choose the channel, pin a
  version and set a minimum version; the server announces the oldest client it still works with.
- **Nothing is trusted that isn't signed.** Update packages carry a minisign signature that binds the
  version; the policy is owner-signed (e2ee.md §11); the package repositories are GPG-signed.

## 2. How each install updates

| Install           | Detected by                                | Updates through                                       |
|-------------------|--------------------------------------------|-------------------------------------------------------|
| Windows NSIS      | bundle type (patched in by the bundler)    | Self-update: the new setup `.exe`, passive mode       |
| Windows MSI       | bundle type                                | Self-update: the new `.msi` via `msiexec /passive`    |
| macOS app (dmg)   | bundle type                                | Self-update: the `.app.tar.gz` replaces the app       |
| AppImage          | bundle type                                | Self-update: the new AppImage replaces the file       |
| deb               | bundle type                                | APT repository; PackageKit button in the app          |
| rpm               | bundle type                                | DNF/zypper repository; PackageKit button in the app   |
| Flatpak           | `FLATPAK_ID` / `/.flatpak-info`            | `flatpak update` (Flathub or a Flatpak remote)        |

Whether a deb or rpm came from the repository is read from the package manager's source files
(`feed::package_source`): an enabled section named `teamcraft…` or with a URL of the package site in
`/etc/yum.repos.d/*.repo` or `/etc/zypp/repos.d/*.repo`, or an enabled `deb` entry for it in
`/etc/apt/sources.list` and `/etc/apt/sources.list.d/*.{list,sources}` (any entry in a file named
`teamcraft…`, for mirrors). Without one the package was installed from a downloaded file.
| Anything else     | (development builds, `cargo run`)          | Nothing; the About section says so                    |

The bundler writes the bundle type into each package's copy of the executable, so one binary knows
whether it was installed from the AppImage, the deb or the rpm (`tauri::utils::platform::bundle_type`).

## 3. Update feed

### 3.1 Manifests

Each release with signed update artifacts carries a `latest.json` in the Tauri updater's static
format, generated by `scripts/updater-manifest.py` in the release workflow:

```json
{
  "version": "1.0.1",
  "notes": "https://github.com/Zeitgleich/TeamCraft/releases/tag/v1.0.1",
  "pub_date": "2026-11-02T10:00:00Z",
  "platforms": {
    "windows-x86_64-nsis":    { "url": ".../TeamCraft_1.0.1_x64-setup.exe",           "signature": "..." },
    "windows-x86_64-msi":     { "url": ".../TeamCraft_1.0.1_x64_en-US.msi",           "signature": "..." },
    "windows-aarch64-nsis":   { "url": ".../TeamCraft_1.0.1_arm64-setup.exe",         "signature": "..." },
    "windows-aarch64-msi":    { "url": ".../TeamCraft_1.0.1_arm64_en-US.msi",         "signature": "..." },
    "darwin-aarch64-app":     { "url": ".../TeamCraft_1.0.1_aarch64.app.tar.gz",      "signature": "..." },
    "darwin-x86_64-app":      { "url": ".../TeamCraft_1.0.1_x64.app.tar.gz",          "signature": "..." },
    "linux-x86_64-appimage":  { "url": ".../TeamCraft_1.0.1_amd64.AppImage",          "signature": "..." },
    "linux-aarch64-appimage": { "url": ".../TeamCraft_1.0.1_aarch64.AppImage",        "signature": "..." }
  }
}
```

- Keys are always `{os}-{arch}-{installer}`. There are deliberately no bare `{os}-{arch}` keys: the
  updater falls back to them, and a deb install must never "update" to an AppImage.
- macOS has one app per architecture (Apple silicon `aarch64`, Intel `x64`). The updater asks for
  the architecture it runs as, so an install of the universal app of releases up to 1.0.0-rc.8 moves
  to the build of its own Mac with its next update (an Intel copy running under Rosetta gets the
  Intel build).
- `notes` is the release page (the in-app "What's new" link), not the notes text.
- `version` is the **tag's** version: a candidate tag `v1.0.0-rc.2` announces `1.0.0-rc.2`, even
  though its packages carry the tree's `1.0.0` (release.md, "Tags"). The app knows its own build
  version the same way (below), so candidates update to later candidates and to the release.

### 3.2 Channels and URLs

| Channel      | Manifest URL                                                                       |
|--------------|------------------------------------------------------------------------------------|
| `stable`     | `https://github.com/<repo>/releases/latest/download/latest.json`                   |
| `prerelease` | `https://<owner>.github.io/<repo>/updates/prerelease/latest.json`                  |
| pinned `X`   | `https://github.com/<repo>/releases/download/vX/latest.json`                       |

- GitHub's "latest release" is the newest published non-prerelease, so `stable` needs no hosting.
- `prerelease` is the newest published release of any kind; the Pages site (§5) republishes it each
  time a release is published. Prerelease users therefore also get stable releases.
- `<repo>` is the repository the release workflow ran in (`TEAMCRAFT_RELEASE_REPOSITORY` at build
  time), so a fork's builds follow the fork's releases.
- A **feed URL** in the policy replaces all of these: organizations can mirror `latest.json` and the
  packages on their own server (air-gapped networks). The signature still has to verify against the
  public key built into the app, so a mirror can withhold updates but never inject one.
- Releases are drafts until a maintainer publishes them; neither URL sees a draft.

### 3.3 Signatures

- Update artifacts are signed with minisign by `cargo tauri signer sign --app-version <version>`.
  The trusted comment carries the version, and the app requires it (`requireSignedVersion`): a
  manifest that pairs a newer version number with an older, validly signed package is rejected, so
  the feed can't downgrade anyone.
- The public key is `plugins.updater.pubkey` in `apps/desktop/tauri.conf.json`. Empty means "this
  build cannot update itself": the app says so instead of checking.
- The release workflow signs only when the secret `TAURI_SIGNING_PRIVATE_KEY` exists. Without it the
  release is built as before, without `.sig` files and without `latest.json`, and the workflow warns.
  With the secret but an empty public key it fails: those builds could never verify their own updates.

## 4. In the app

### 4.1 Checking

- First check 1–10 minutes after start (random), then every 24 hours ± 2 hours (random). The jitter
  keeps a whole organization from hitting the feed in the same minute after a holiday.
- "Check now" in Settings → Advanced → Updates checks immediately.
- A check is a plain GET of the manifest; no identifiers are sent besides what any HTTP request
  carries.

### 4.2 Preference (per device, Settings → Advanced → Updates)

| Preference           | Behaviour                                                                   |
|----------------------|-----------------------------------------------------------------------------|
| Automatic (default)  | Download in the background; "Restart to update"; installs on quit as well   |
| Notify only          | Show "Update available"; downloads only when the user clicks                |
| Off                  | No checks                                                                   |

### 4.3 What the user sees

- An update that is found but not downloaded (notify only): a banner "TeamCraft 1.0.1 is
  available" with "Download", "What's new" (the release page) and "Later", which hides that version
  until the next launch.
- An update that is downloaded and verified: a blue banner at the top (the accent colour) that
  stays until the app restarts and can't be dismissed: "TeamCraft 1.0.1 is ready — restart to
  update", with "Restart" and "What's new" (#729). It is the one banner meant to be seen; the
  connection state, by contrast, is a quiet hint along the top bar. The same banner follows a
  package-manager update (§4.5): "TeamCraft 1.0.1 is installed — restart to use the new version".
- During a call nothing is downloaded and nothing restarts: the banner stays, its button is
  disabled and reads "Restart after the call", and an update that is ready is not installed when
  the app quits mid-call.
- One banner from the click to the restart (#1044): "Download" or "Update now" turns into a
  disabled button with a spinner and the progress ("Downloading… 42 %", "Installing 1.0.1…",
  "Waiting for authorization…" while polkit asks), and the same banner then becomes the ready one;
  the colours cross-fade, nothing jumps. An automatic download stays quiet until it is ready. A
  failed download or install keeps the offer: the error shows in the banner, next to the button
  that tries again.
- deb/rpm from the repository: "TeamCraft 1.0.1 is available. Update it with your package manager"
  plus the command with a copy button (`sudo apt update && sudo apt install --only-upgrade
  team-craft`, or `sudo dnf upgrade --refresh team-craft`) and, when PackageKit runs, an "Update
  now" button (§4.5).
- deb/rpm installed from a file (no repository configured): "Download the new package", which
  links the release asset for this architecture (the release page for candidates, or for a
  mirrored feed), and "Add the repository for automatic updates", which links the package site
  (§5).
- Flatpak: the same check, and "Update it with Flatpak or your software center" with
  `flatpak update de.zeitgleich.teamcraft`.
- AppImage in a directory the app can't write (the updater moves the file aside and writes the new
  one next to it): "Download the new AppImage", linking the manifest's AppImage, instead of a
  download that would fail on restart.
- Hiding the banner (`UpdateStatus::dismissal`): an update the app installs itself and that waits
  for its restart can't be hidden (#729); one it hasn't downloaded yet has "Later" until the next
  launch. Where the app can't install the update (deb, rpm, Flatpak, a read-only AppImage), the hint
  has "Dismiss", which the shell keeps in `updates.json` for that version: the next version shows
  again.
- Below the minimum version (§4.4): a banner that stays, "This version of TeamCraft is too old for
  your organization. Please update.", with the update button where the install can update itself.

### 4.4 Organization control

The owner-signed workspace policy (admin.md §2.3) has a `client_updates` part, edited in the admin
console under *Updates*:

| Field               | Default   | Meaning                                                                                 |
|---------------------|-----------|-----------------------------------------------------------------------------------------|
| `mode`              | `allowed` | `allowed`: devices follow their preference. `disabled`: no self-updates (IT deploys)    |
| `channel`           | `stable`  | `stable` or `prerelease`                                                                |
| `pinned_version`    | none      | Only this version is installed (and only if it is newer than the running one)           |
| `minimum_version`   | none      | Clients below it show "please update"                                                   |
| `feed_url`          | none      | Mirror of `latest.json` (https only); replaces the channel URLs                         |

- Clients follow only an owner-signed policy, so a compromised server can't switch updates off or
  redirect them (it can always withhold the policy, which leaves the defaults).
- The last verified policy is cached by the desktop shell, so it applies before sign-in on the next
  start as well.
- Machine-wide: the environment variable `TEAMCRAFT_DISABLE_UPDATES=1` (set by group policy, MDM or a
  packager) turns self-updates off whatever the policy says.
- The **server** announces `GET /api/v1/client-compatibility` (no sign-in needed):
  `{ "server_version": "1.0.0", "minimum_client_version": "1.0.0" }`. The effective minimum is the
  higher of that and the policy's `minimum_version`. The server's value is compiled in: it moves
  only when a release breaks compatibility with older clients (release.md: 1.x stays compatible).

### 4.5 PackageKit (deb/rpm)

The app can't and shouldn't replace files owned by the package manager. Two approaches were weighed:

- Shelling out to `pkexec apt-get …` / `pkexec dnf …`: distribution-specific, needs root for the
  whole command line, and bypasses the desktop's software center.
- **PackageKit over D-Bus** (chosen): one distribution-neutral API that GNOME Software and KDE
  Discover use themselves. The app refreshes the cache, finds the `team-craft` update and asks
  PackageKit to install it with `ONLY_TRUSTED`, so the repository signature is checked by the
  package manager; polkit asks the user for authorization. The app follows each transaction's
  `Status` (`PropertiesChanged`) and the banner says when PackageKit waits for that authorization.
  Without PackageKit on the bus the button is hidden and the command stays.

After a package update the running app is the old version; the banner then stays and offers
"Restart" (§4.3).

## 5. Package repositories and the Pages site

`.github/workflows/packages.yml` runs when a release is **published** (and by hand). It rebuilds a
GitHub Pages site from the published releases, so the site never has state of its own:

```
index.html, style.css, site.js    landing page with the downloads (scripts/package-site-page.py)
fonts/                            the page's fonts (Inter, JetBrains Mono; SIL OFL), self-hosted
updates/stable/latest.json        newest stable release
updates/prerelease/latest.json    newest release of any kind
apt/dists/{stable,prerelease}/    signed Release/InRelease, Packages for amd64 and arm64
apt/pool/<tag>/*.deb
rpm/{stable,prerelease}/          rpms signed with rpmsign, repodata with a signed repomd.xml
teamcraft-archive-keyring.gpg     the repository key (binary, for Signed-By)
teamcraft-archive-keyring.asc     the same key, armored (for rpm/dnf)
fdroid/repo/                      F-Droid repository of the libre Android app (§8)
fdroid/qr.svg, fingerprint.txt    its QR code and key fingerprint, shown on the page
site-build.txt                    the workflow run that built the site (checked after deploying)
```

Debian and Ubuntu (deb822 sources):

```sh
curl -fsSL https://zeitgleich.github.io/TeamCraft/teamcraft-archive-keyring.asc \
  | sudo gpg --dearmor -o /usr/share/keyrings/teamcraft-archive-keyring.gpg
sudo tee /etc/apt/sources.list.d/teamcraft.sources >/dev/null <<'EOF'
Types: deb
URIs: https://zeitgleich.github.io/TeamCraft/apt
Suites: stable
Components: main
Signed-By: /usr/share/keyrings/teamcraft-archive-keyring.gpg
EOF
sudo apt update && sudo apt install team-craft
```

Fedora, RHEL and openSUSE:

```sh
sudo tee /etc/yum.repos.d/teamcraft.repo >/dev/null <<'EOF'
[teamcraft]
name=TeamCraft
baseurl=https://zeitgleich.github.io/TeamCraft/rpm/stable
enabled=1
metadata_expire=1h
gpgcheck=1
repo_gpgcheck=1
gpgkey=https://zeitgleich.github.io/TeamCraft/teamcraft-archive-keyring.asc
EOF
sudo dnf install team-craft
```

(openSUSE: put the same file into `/etc/zypp/repos.d/`, add `autorefresh=1`, and `zypper install
team-craft`.) For release candidates use the suite or directory `prerelease`, shown as "Beta" on the
site and in the app; it also receives every stable release.

How soon a new version reaches the package manager (#694):

| Package manager | Reads the repository metadata                                   | Without a manual refresh    |
|-----------------|-----------------------------------------------------------------|-----------------------------|
| dnf             | when its cached copy is older than `metadata_expire`            | within 1 hour               |
| apt             | only on `apt update` (PackageKit and unattended-upgrades daily) | after the next daily run    |
| zypper          | before each command with `autorefresh=1`, else `zypper ref`     | at once with `autorefresh`  |

- dnf's default `metadata_expire` is 48 hours, so up to 1.0.7 a new version showed only after
  `dnf upgrade --refresh` or two days. The `.repo` files on the site set `metadata_expire=1h`, and
  the rpm's `%post` (`apps/desktop/packaging/linux/rpm-post-install.sh`) adds it to TeamCraft
  repository files written before, so existing installs pick it up with their next update. It
  leaves a file alone that sets its own `metadata_expire` or defines other repositories too. The rpm
  doesn't ship the `.repo` file itself: Tauri's rpm bundler can't mark it `%config(noreplace)`, and a
  plain file would undo the user's changes on every update (and add a repository to installs from a
  downloaded rpm).
- apt has no expiry of its own: the `Release` file carries no `Valid-Until`, so a cached index never
  goes stale or fails as expired, and apt sees a new version as soon as `apt update` runs. The
  in-app command therefore starts with `apt update`; the "Update now" button refreshes through
  PackageKit first (§4.5), which on dnf systems honours `metadata_expire`.
- The host is not the cause: GitHub Pages (and Cloudflare Pages alike) let caches keep a file for
  minutes (`Cache-Control: max-age=600` on GitHub Pages), not days. Moving the site would not change
  it.

- Candidate packages carry the release version (`1.0.0` for `v1.0.0-rc.2`), so the package manager
  doesn't move from a candidate to the release with the same number; reinstall in that case.
- The rpms on the site are signed copies; their checksums differ from the release assets (the
  release's `SHA256SUMS` and attestations cover the unsigned originals).
- The landing page is generated from what the run publishes: download buttons link the assets of
  the newest stable release and the newest prerelease (only files that exist; the visitor's system is
  preselected), setup snippets appear only for repositories that were built, and while there is no
  stable release the page says so and shows the prerelease channel. It is self-contained (no external
  fonts, scripts or trackers; strict CSP). Its static files are in `scripts/site/`, its fixed
  illustrations (drawn in HTML/CSS with the app's colours) in `scripts/site-parts/`. The workflow fails
  when any page or style sheet links a file of the site that doesn't exist (`package-site-page.py
  check`). Debug-signed APKs get a test-build warning; once a release has signed release APKs, only
  those are offered.
- Store listings appear once the repository variables `PLAY_STORE_URL` / `APP_STORE_URL` are set.
- One-time setup: *Settings → Pages → Source: GitHub Actions*.
- The deb/rpm "update available" notice reads the same `latest.json` as the self-updating installs, so
  it needs the updater key as well (§7).
- GitHub Pages sites are limited to 1 GB. The site holds two releases' debs and rpms (about 0.7 GB
  today); if packages grow past that, the same script can publish to any static host or bucket.

## 6. Flatpak

The Flatpak never updates itself (the sandbox can't, and shouldn't, write its own files). It checks
the feed like every other install and shows `flatpak update de.zeitgleich.teamcraft` (§4.3). Today
the release attaches single-file bundles, which `flatpak install --bundle` installs without an
update source; for those the release page ("What's new") has the new bundle. The plan:

1. **Flathub** (preferred): submit `apps/desktop/packaging/linux/de.zeitgleich.teamcraft.yml`; then
   `flatpak update` and the software centers update it.
2. Until then, or for organizations that want their own: a Flatpak repository (`flatpak
   build-update-repo`, GPG-signed) next to APT and RPM on the Pages site, with a `.flatpakrepo` file.

## 7. Secrets and one-time setup

| Secret                               | What                                                     |
|--------------------------------------|----------------------------------------------------------|
| `TAURI_SIGNING_PRIVATE_KEY`          | Content of the minisign private key file (updater)       |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | Its password                                             |
| `LINUX_REPO_GPG_PRIVATE_KEY`         | ASCII-armored GPG private key for APT/RPM signing        |
| `LINUX_REPO_GPG_PASSPHRASE`          | Its passphrase                                           |
| `FDROID_KEYSTORE_BASE64` and others  | F-Droid repository key (§8.3)                            |

Updater key (on a trusted machine, never in CI):

```sh
cargo tauri signer generate -w ~/.tauri/teamcraft-updater.key
gh secret set TAURI_SIGNING_PRIVATE_KEY < ~/.tauri/teamcraft-updater.key
gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD     # the password chosen above
cat ~/.tauri/teamcraft-updater.key.pub                # into plugins.updater.pubkey, then commit
```

Repository key:

```sh
gpg --quick-generate-key "TeamCraft packages <packages@example.com>" ed25519 sign 3y
gpg --armor --export-secret-keys <fingerprint> | gh secret set LINUX_REPO_GPG_PRIVATE_KEY
gh secret set LINUX_REPO_GPG_PASSPHRASE
```

Ed25519 is supported by current APT and by rpm 4.16 and later (Fedora, RHEL 9 and newer); signing,
repository metadata and installing were tested on Ubuntu 24.04 and Fedora 43. Older systems such as
RHEL 8 (rpm 4.14) or Ubuntu 18.04 can't be served with it; to support them, use `rsa4096` instead.

Keep offline backups of both private keys. Losing the updater key means every installed app has to be
updated by hand once (a new key ships with that version); a leaked key means an attacker who also
controls the feed can push updates: rotate it with a release that carries the new public key, signed
with the old one.

## 8. F-Droid repository (Android)

The libre Android app (`de.zeitgleich.teamcraft.libre`, push through UnifiedPush, no Google
services) has its own F-Droid repository on the Pages site. Users add it once in F-Droid, Droid-ify or
Neo Store and the app updates with their other apps. The `full` flavor stays with Google Play and the
release APK.

### 8.1 Adding it

The site's "Updates through F-Droid" section (`#fdroid`) has an "Add to F-Droid" button
(`fdroidrepos://` link) and a QR code; both carry the fingerprint, so the client checks the
repository key from the first download on. By hand: F-Droid → Repositories → Add repository → the
address `https://zeitgleich.github.io/TeamCraft/fdroid/repo`, then compare the fingerprint the app
shows with the one on the page.

### 8.2 How it is built

`scripts/fdroid-repo.py`, called by `packages.yml` after the APT/RPM repositories are built:

- `fetch` downloads `teamcraft-android-X.Y.Z-libre-release.apk` of the newest published **stable**
  releases that have one (3 by default; repository variable `FDROID_KEEP_VERSIONS`, about 85 MB
  each, so the Pages site stays well below its 1 GB limit). Releases without the signed libre APK
  (Android build failed, no upload key) are skipped; candidates are not in the repository.
- `build` runs `fdroid update` (fdroidserver, pinned in the workflow) on them with the store listing
  from `apps/android/store` (texts, icon, feature graphic, screenshots; the Firebase line of the
  description is replaced, the libre app has none), the licence, source, issue and changelog links,
  and per version the release's highlights as "What's new". The "added" date of a version is its
  release's publication, so a rebuild doesn't redate old versions.
- The APKs are the release files as they are, signed with the app key (`apps/android/README.md`,
  "Signing"), so the GitHub APK, the F-Droid install and (for the full flavor) Google Play share one
  signature: an install from the release APK updates through F-Droid and the other way round.
- Before publishing, the script checks that the index lists every fetched version, that all are
  signed with one key, that each has its changelog, and that `index-v1.jar` and `entry.jar` are
  signed with the repository key. `index-v2.json`/`entry.jar` serve current F-Droid clients;
  fdroidserver also writes `index-v1.jar` (and the older v0 index), which Droid-ify, Neo Store and
  older F-Droid versions still read.
- The finished repository goes into the site with one rename; the Pages deployment then replaces the
  whole site at once, so a client never sees a new index with missing APKs.
- The step is optional: without the key, or when it fails, the site is built and published without
  the F-Droid repository (a warning in the run) and APT, RPM and the manifests are unaffected. Like
  the rest of the site it has no state: the next run rebuilds it, and re-running `android-release`
  for a release whose Android build was late starts the site build again (release.md).
- F-Droid checks the repository about once a day (and on a pull to refresh), so a nightly release
  reaches it within a day of publication.

### 8.3 Key and secrets

The repository key signs the index only; it is not the app signing key, and losing it means users
have to remove and re-add the repository (the apps stay installed). Create it once on a trusted
machine, keep an offline backup, and never commit it:

```sh
keytool -genkeypair -v -storetype PKCS12 -keystore teamcraft-fdroid.p12 -alias fdroid \
  -keyalg RSA -keysize 4096 -validity 10000 -dname "CN=TeamCraft F-Droid repository"
base64 -w0 teamcraft-fdroid.p12 | gh secret set FDROID_KEYSTORE_BASE64
gh secret set FDROID_KEYSTORE_PASSWORD   # the store password chosen above
gh secret set FDROID_KEY_PASSWORD        # PKCS12: the same password
gh secret set FDROID_KEY_ALIAS --body fdroid
```

| Secret                     | What                                         |
|----------------------------|----------------------------------------------|
| `FDROID_KEYSTORE_BASE64`   | The PKCS12 keystore file, base64             |
| `FDROID_KEYSTORE_PASSWORD` | Its store password                           |
| `FDROID_KEY_ALIAS`         | Alias of the key in it (`fdroid` above)      |
| `FDROID_KEY_PASSWORD`      | The key's password (PKCS12: the store's)     |

The fingerprint users compare is the SHA-256 of the key's certificate; the site shows it, and
`keytool -list -v -keystore teamcraft-fdroid.p12` prints it (without the colons, upper case).

Test it without the real key:

```sh
keytool -genkeypair -storetype PKCS12 -keystore /path/to/test.p12 -alias fdroid -keyalg RSA \
  -keysize 4096 -validity 365 -dname "CN=test" -storepass testpass -keypass testpass
export FDROID_KEYSTORE=/path/to/test.p12 FDROID_KEYSTORE_PASSWORD=testpass \
  FDROID_KEY_ALIAS=fdroid FDROID_KEY_PASSWORD=testpass
scripts/fdroid-repo.py fetch --work /path/to/work --repo Zeitgleich/TeamCraft --keep 2
scripts/fdroid-repo.py build --work /path/to/work --site /path/to/site \
  --site-url http://10.0.2.2:8765 --repo Zeitgleich/TeamCraft
(cd /path/to/site && python3 -m http.server 8765)
```

The Android emulator reaches the host as `10.0.2.2`; add `http://10.0.2.2:8765/fdroid/repo` by hand
(the `fdroidrepos://` link is https only).
