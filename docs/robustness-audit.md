# Robustness audit

Status of every v1 feature (PLAN.md rows marked v1) under real-world conditions: network loss and
change, offline actions, app lifecycle, hostile networks, multi-device use, server restarts, large data
and clock skew. The checklist itself is [.claude/rules/robustness.md](../.claude/rules/robustness.md);
this document records where the code stands against it. Calls (reconnect, network handover, SFU
restart) are audited and fixed separately and are left out here.

**Method.** Code reading of the server, core, crypto, UI, desktop, Android and iOS code at `main`
1c133c9 (October 2026), split by area, with every finding traced to a file and line. The findings that
are fixed in this change were reproduced first with a failing test (fake server, paused clock) where
the condition can be simulated. Nothing was tested on devices or against real proxies; rows that
depend on that say "unverified".

**Reading the tables.** *Verdict*: `ok`, `gap`, `fixed here` (fixed in the change that added this
document, see the list below) or `unverified`. *Severity*: critical (data loss, broken encryption or a
feature that stops working for good), high (feature fails under a common condition), medium, low.
*v1 blocker*: must be solved before v1.0.0. *Evidence*: line numbers refer to 1c133c9; short path
prefixes are `core/` = `crates/teamcraft-core/src/`, `server/` = `crates/teamcraft-server/src/`,
`crypto/` = `crates/teamcraft-crypto/src/`, `db/` = `crates/teamcraft-db/`, `ui/` =
`crates/teamcraft-ui/`, `ffi/` = `crates/teamcraft-ffi/src/`, `desktop/` = `apps/desktop/src/`,
`android/` = `apps/android/app/src/main/java/de/zeitgleich/teamcraft/`, `ios/` = `apps/ios/`; other
paths are relative to the repository root. Each open gap points to a brief (B1-B15) at the end that a
separate session can pick up.

### Re-check of the server and the web client (cloud run, October 2026)

At `main` dd957c6 the server and web rows were checked again, this time by running them: the e2e
suite `server_robustness.rs` against the real server binary (restart and SIGTERM, resume, gap and
expired window, concurrent retries, read positions, Postgres cut off at runtime and at startup,
stalled consumers, process memory and CPU) and the web benchmark `perf.rs` on the large workspace;
numbers and method in [performance.md](performance.md). Android, iOS and desktop rows were not
re-checked (no devices in that environment). Rows marked `fixed (cloud)` were fixed in the same
change, each with a test that failed before; `gap (measured)` replaces an earlier `unverified` with
what was observed. B2, B3 and B11 had been done meanwhile (commits c8256a7 and 0156647); their rows
are marked `fixed (B2)`, `fixed (B3)`, `fixed (B11)` from the code, not re-tested here.

New issues from the measurements (milestone v1.1): #246 (every change re-reads the whole workspace,
7 % idle CPU and 63 requests per minute on the large workspace), #247 (three minutes until the
channel list shows after coming back to a workspace that grew by 100k messages) and #248 (wasm at
9.4 of 10 MB, no size check). The measured server gaps that remain are in #156 (SIGTERM without
close frames, gateway memory bounded by count).

A later change took on #246, #247, #252 and #259 and re-measured both workspaces (performance.md,
"Idle traffic and updates per conversation"): no API requests while idle, change notifications per
conversation, the channel list after 1.6 s instead of four minutes on the large workspace. It found
two more gaps: a full sync longer than the server's heartbeat timeout loses its connection (row
"Long full sync", fixed with #325), and the web core stalled on IndexedDB's write backlog (fixed).

### Gateway, offline actions and rings (October 2026)

Issues #156, #159 and #142 were worked in one change, each condition with a test (hub and core tests
on paused clocks and the fake server; server tests against Postgres):

| Commit                                                                   | Area    |
|--------------------------------------------------------------------------|---------|
| Drop queued ring retries once the call stops ringing                     | Push    |
| Gateway: shared events, byte-bounded buffers, resume race, drain         | Server  |
| Queue read markers, acks, pins and presence offline; resilient full sync | Offline |

Review follow-ups: a process-wide byte budget for all resume buffers (`[gateway] max_buffered_bytes`,
the slowest sessions go first), a server test for a real restart (fresh hub: `session_invalid`, then a
full sync), member and content resync tracked apart, and the offline queue stored one record per entry
(unknown kinds skipped, compare-and-swap per entry) and flushed in queue order with per-entry backoff,
an attempt cap and an age cap.

Still open from B10: a load test at 500 members x 1 MiB with a stated budget (the hub tests prove the
per-session and process-wide bounds of the buffers, not process RSS), a startup check against a second instance, and a restart that is
cheaper than a fleet-wide full sync (durable per-user cursor). From B14: refetching the call roster,
meetings and profile updates after a fresh session.

## Briefs for larger gaps

### B1 Single owner of a device's store (web tabs, desktop instances) – critical, v1 blocker

- **Scope:** only one core may own a device's store at a time. Web: take a Web Lock
  (`navigator.locks.request("teamcraft-core-<user>", { ifAvailable: true })`) before opening
  IndexedDB; other tabs become followers (UI only, fed over `BroadcastChannel`) or show "TeamCraft is
  open in another tab". Promote a follower when the owner closes. Handle `versionchange`. Desktop:
  single-instance on every OS (the plugin is Windows-only today) plus an OS file lock on the store.
- **Files:** `crates/teamcraft-ui/src/web_core.rs`, `crates/teamcraft-core/src/store/browser/*`,
  `crates/teamcraft-core/src/store/sealed_sqlite.rs`, `apps/desktop/src/main.rs`, `apps/desktop/Cargo.toml`.
- **Done:** a browser test with two tabs sending alternately never forks an MLS epoch or sends twice; a
  second desktop instance focuses the first instead of opening the store; docs/e2ee.md updated.

### B2 MLS commit loss and desync self-heal – critical, v1 blocker

- **Scope:** in `post_commit`, discard the pending commit only on `EpochConflict`; on other errors keep
  it and, when the own commit later shows up in the backlog, merge it (compare bytes) instead of
  processing it. Detect a device that fell out of a group (`NeedsBacklog`, rejected commit while others
  moved on) and heal it: drop the local group and get re-added through the existing
  `add_missing_devices` path (or an external commit), without user action. Take the local clock out of
  merge decisions (roster freshness, removed-sender cutoff use server time). Flush the outbox only after
  MLS catch-up.
- **Files:** `crates/teamcraft-core/src/client/{groups,gateway,messaging}.rs`, `runner.rs`,
  `crates/teamcraft-crypto/src/mls/group.rs`, server `services/mls.rs`, the fake API (an "applied,
  response lost" mode), docs/e2ee.md §4.6.
- **Done:** fake-server tests for "commit applied, response lost" and a forced desync end with all
  devices in the same epoch; a 10-minute client clock offset changes nothing.

### B3 Key package lifecycle – critical, v1 blocker

- **Scope:** record each key package's expiry on the server, never hand out expired ones, delete them;
  report "expiring soon" and "has a valid last-resort package"; replace packages inside a renewal window
  and rotate the last-resort package on a timer, not only in full sync. Skip (log) invalid packages of
  one device instead of failing to add the whole user.
- **Files:** `crates/teamcraft-crypto/src/mls/mod.rs`, `crates/teamcraft-core/src/client/{sync,groups}.rs`,
  `runner.rs`, server `services/key_packages.rs`, `crates/teamcraft-db/src/key_package.rs` plus a
  migration, proto key package types.
- **Done:** with a fake clock at +100 days a user can still be added; expired packages are never
  served; a user with one revoked device and one good device is added with the good one.

### B4 One connection supervisor and connection state – high, v1 blocker (network change, banner)

- **Scope:** replace the three loops (`runner.rs`, `web_core.rs`, desktop `runtime.rs`) with one in
  `teamcraft-core`: jittered backoff that resets only after a stable connection, handshake timeouts,
  heartbeat from `hello`, and a `ConnectionState { Connecting, Connected, Offline { retry_at },
  SignInRequired }` for the shells. Hooks that reconnect at once: FFI `network_changed()` from Android
  `NetworkCallback` and iOS `NWPathMonitor`, browser `online`/`visibilitychange`/`resume`, desktop OS
  wake (logind `PrepareForSleep`, `NSWorkspaceDidWakeNotification`, `WM_POWERBROADCAST`). A per-request
  deadline for small API calls (Apple, Windows). Banners and per-message pending/failed state on every
  platform driven by the core, not by OS connectivity. Gateway auth failures surface as "sign in again"
  and don't count as guessing on the server.
- **Files:** `crates/teamcraft-core/src/{runner.rs,client/gateway.rs,api/http.rs}`,
  `crates/teamcraft-ui/src/{web_core.rs,components/offline_banner.rs}`, `apps/desktop/src/core/runtime.rs`,
  `crates/teamcraft-ffi`, `apps/android/.../ui/Connectivity.kt`, `apps/ios/TeamCraft/Model/NetworkMonitor.swift`,

- **Done:** fake-gateway tests (paused clock) for silent death, stalled handshake, network change
  (reconnect < 5 s) and wake; one implementation used by all shells; "online but disconnected" visible
  on every platform.

### B5 Streaming, resumable transfers off the sync loop – v1.1 (#153)

- **Scope:** encrypt with the existing streaming `AttachmentEncryptor` into S3 multipart parts with
  presigned part URLs (server: create, sign part, complete, abort; the sweeper aborts stale uploads).
  Persist upload ID, key, finished parts and offset so a restart continues at the next part. Download
  as a streaming, Range-resumable GET into a `.part` file with an incremental hash and a size cap. Run

- **Files:** `crates/teamcraft-core/src/client/{attachments,files}.rs`, `ui_files.rs`, `runner.rs`,
