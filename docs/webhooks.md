# Outgoing webhooks

The integration bridge ([bridge.md](bridge.md)) brings events *into* encrypted channels. Outgoing
webhooks are the other direction: the server tells external systems (a ticket system, a CI job, a
chat-ops tool) that something happened in TeamCraft. Issue #847.

## 1. What is sent, and what never is

The server is untrusted and cannot read messages (ARCHITECTURE.md §2). A webhook therefore carries
only metadata the server already sees: **IDs and times**. No channel or space names, no topics, no
display names, no message content, no file names. A receiver that wants names looks them up through
the API with its own credentials, under the normal permission checks.

Only **channels** are reported. Direct and group messages are private conversations; nothing about
them (not even that a call took place) goes out.

| Event                | When                                                   | `data`                                              |
|----------------------|--------------------------------------------------------|-----------------------------------------------------|
| `channel.created`    | A channel was created                                  | `conversation_id`, `actor_id`                       |
| `channel.archived`   | A channel was archived                                 | `conversation_id`, `actor_id`                       |
| `channel.unarchived` | An archived channel was restored                       | `conversation_id`, `actor_id`                       |
| `channel.deleted`    | A channel was deleted                                  | `conversation_id`, `actor_id`                       |
| `member.joined`      | Somebody joined a channel or was added                 | `conversation_id`, `actor_id`, `subject_id`         |
| `member.left`        | Somebody left or was removed (`actor_id ≠ subject_id`) | `conversation_id`, `actor_id`, `subject_id`         |
| `call.started`       | The first person joined a channel's call               | `conversation_id`, `actor_id`, `call_id`            |
| `call.ended`         | The last person left a channel's call                  | `conversation_id`, `call_id`                        |
| `ping`               | The console's "Send test" button                       | –                                                   |

Event names are a wire enum: receivers must ignore types they don't know, new ones will be added.

Not in scope: forwarding message **content**. The server can't; it would have to be a bot that is a
member of the channel and decrypts as one (the bridge), visible to everybody in the member list. That
is a separate feature, if wanted.

## 2. The request

```http
POST /hooks/teamcraft HTTP/1.1
Content-Type: application/json
User-Agent: TeamCraft-Webhooks/1.0.25
webhook-id: 7329847291837440001
webhook-timestamp: 1762700000
webhook-signature: v1,<base64 of the HMAC>

{"id":"7329847291837440001","type":"member.joined","created_at":1762699999812,
 "data":{"conversation_id":"7329847291837439000","actor_id":"…","subject_id":"…"}}
```

IDs are decimal strings (they don't fit a JavaScript number). `created_at` is the server's time of
the event in milliseconds; `webhook-timestamp` is the time of *this attempt* in seconds.

### 2.1 Signature

The scheme is the [Standard Webhooks](https://www.standardwebhooks.com/) specification, so receivers
can use its libraries:

- Each webhook has a random 256-bit secret, shown once in the console as `whsec_<base64>`.
- `webhook-signature` is `v1,` and the base64 of HMAC-SHA-256(secret, `{webhook-id}.{webhook-timestamp}.{body}`).
- A receiver recomputes it over the raw body, compares in constant time, and **rejects timestamps
  more than 5 minutes from its clock**: the timestamp is signed, so an old request can't be replayed
  with a fresh one. Within the window, `webhook-id` lets it drop duplicates.

The implementation is `teamcraft_crypto::webhook` (HMAC from RustCrypto `hmac`/`sha2`, checked
against the specification's example). The secret is generated by the server, sealed with the
settings key (`[secrets]`) under the associated data `webhook.<id>` so a sealed secret can't be
moved to another row, and never returned after creation. "New secret" replaces it at once; there is
no overlap period, so rotate when the receiver can be updated right away.

### 2.2 Answers

| Answer                                  | Meaning                                                              |
|-----------------------------------------|----------------------------------------------------------------------|
| 2xx                                     | Delivered.                                                           |
| 5xx, 408, 429, timeout, connection error | Temporary: tried again with backoff; `Retry-After` is honoured.      |
| any other 4xx, 3xx                      | Refused for good: the event is dropped and logged. No retry.        |

Redirects are never followed (a redirect could point anywhere, and the signature is for this URL).
The answer's body is never read or stored.

## 3. Delivery and robustness

Events are queued in Postgres (`webhook_deliveries`, migration 0092), one row per subscribed
webhook, with the JSON body fixed at the time of the event so every attempt sends the same bytes.

- **Restart and crash:** a worker claims the oldest due row together with its webhook
  (`FOR UPDATE SKIP LOCKED`) and keeps the transaction open while it sends. A killed server releases
  the claim with its connection: the event stays queued and is sent after the restart, with the same
  `webhook-id`. Delivery is therefore *at least once*; receivers deduplicate on the ID.
- **One request in flight per target:** the webhook row is locked with the delivery, so a slow
  target is not hit in parallel, and several workers serve several targets.
- **Backoff per target, not per event:** after a failure the whole webhook pauses (10 s, doubling
  per failure in a row, equal jitter, capped at one hour; `Retry-After` up to twice the cap). A
  target that is down gets one attempt per step, not one per queued event, and once it is back the
  queue drains oldest first instead of arriving as a burst of retries.
- **Bounds:** at most `max_queued_per_webhook` (1000) waiting events per webhook, further ones are
  dropped and counted; events older than `max_age_hours` (24) are dropped by a sweep every 10
  minutes; an event is given up after `max_attempts` (12). The log keeps the last 50 attempts per
  webhook. Disabling a webhook empties its queue, so turning it back on does not send a day of old
  events at once. At most 20 webhooks per instance.
- **Order:** events go out in event order per webhook, but a receiver should not depend on it
  (a dropped event leaves a gap).
- **Time:** the receiver's replay window depends on both clocks; servers run NTP. Backoff and expiry
  use the database's clock.
- **Workers:** `[webhooks].workers` (2) tasks, woken at once by a new event, otherwise every
  `poll_interval_secs` (15) — the poll only finds deliveries whose backoff ended.

## 4. SSRF protection

A webhook URL is chosen by a workspace admin, but the request comes from the server, inside its
network. Without protection an admin could reach the cloud metadata service, the database or the
admin ports of other services.

- The URL must be `https`, without user or password, and its host is checked by its text: no IP
  literal in a private, loopback, link-local, CGNAT, documentation, multicast or reserved range,
  IPv4 or IPv6 (including IPv4-mapped, NAT64, 6to4 and Teredo forms), and no `localhost`, `.local`,
  `.internal` or single-label name (`crate::outbound`, shared with Web Push and the holiday feed).
- Names are resolved by `PublicOnlyResolver` at connect time, which drops every non-public address:
  the connection goes to an address checked right then, so DNS rebinding between check and connect
  doesn't help. Dual stack: both A and AAAA answers are checked.
- No proxy from the environment (a proxy would resolve names itself), no redirects.
- Connect timeout 5 s, request timeout 10 s.

`[webhooks].allow_private_targets = true` turns the address checks off and allows plain `http`, for
targets on the operator's own network. It is a file setting on purpose: it widens what the server
can reach, which is the operator's decision, not a console admin's. The console shows whether it is
on.

## 5. Console

Admin console → Webhooks (permission `manage_workspace` on the instance):

- Add a webhook: URL, optional description, the events, on/off. The secret is shown once.
- Per webhook: status (active, off, failing), waiting and dropped events, last delivery and last
  failure with its error (a status code or connection error, never a response body), the next
  attempt while it backs off; Edit, Send test, New secret, Deliveries (the last 50 attempts), Delete.
- Every change is in the audit log (`webhook_created`, `webhook_updated`, `webhook_deleted`,
  `webhook_secret_rotated`, `webhook_test`) with the target's host only: a URL's path or query may
  carry a token.

API: `GET/POST /api/v1/admin/webhooks`, `PUT/DELETE /api/v1/admin/webhooks/{id}`,
`POST …/{id}/secret`, `POST …/{id}/test`, `GET …/{id}/deliveries` (OpenAPI under `admin`).

## 6. Configuration

```toml
[webhooks]
allow_private_targets = false
workers = 2
connect_timeout_secs = 5
request_timeout_secs = 10
max_queued_per_webhook = 1000
max_attempts = 12
initial_retry_delay_secs = 10
max_retry_delay_secs = 3600
max_age_hours = 24
log_entries_per_webhook = 50
poll_interval_secs = 15
```

The webhooks themselves are runtime settings in the database; the file only bounds what they may
cost the server.

## 7. Robustness checklist (robustness.md)

| Condition                | Behaviour                                                                                     |
|--------------------------|-----------------------------------------------------------------------------------------------|
| Target down or slow      | Backoff per target, one request in flight, timeouts per phase; queue bounded, then dropped.   |
| Server restart / crash   | Queue in Postgres; an in-flight claim rolls back and is sent again (same `webhook-id`).       |
| Several server instances | Workers on every instance claim different rows (`SKIP LOCKED`); one request per target.      |
| Postgres briefly down    | Enqueue fails and is logged (the action itself happened, the event is lost); workers retry.   |
| Duplicate delivery       | Possible (at least once); receivers deduplicate on `webhook-id`.                              |
| Hostile target           | No redirects, body not read, errors trimmed to 300 characters, SSRF checks above.             |
| Large instance           | Enqueue is one statement over the (≤ 20) webhooks; no work when nobody subscribes.            |
| Clock skew               | Receiver window ±5 min on the signed timestamp; server-side times from Postgres.              |
| Multi-device / offline   | Not applicable: server-side only.                                                             |

Known gap: an event raised while Postgres is unreachable is not queued (the same as system events).
